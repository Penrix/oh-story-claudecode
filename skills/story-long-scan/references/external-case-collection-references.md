# 外部参考：网文 Case 采集、榜单样本池与书单扩展

> 状态：参考资料，不是当前实现规范。  
> 记录日期：2026-09-18  
> 当前主线以 `story-long-scan/SKILL.md` 为准；本文件只保存可借鉴的项目、文档与工程思想，防止后续重复调研。

---

## 0. 我们自己的方向

当前 Case 采集目标不是“做一个排行榜分析器”。

我们的定义是：

```text
真实市场成绩
只负责第一层过滤
↓
取得真实作品
↓
书名 + 完整简介
↓
榜单书作为锚点
↓
沿真实读者书单继续扩展
↓
和历史 Case 池合并、去重、长期累积
↓
原始 Case 直接参加故事 Seed 创作
```

当前明确原则：

- **起点优先**。先把起点榜单、详情、书单、累积池跑扎实，其他平台后接。
- 榜单只承担“市场过滤器”作用，不研究排名本身。
- 不区分新书、旧书、连载、完结；这些都只是进入候选池的不同入口。
- 最终创作输入只保留：`书名 + 完整简介`。
- 简介不截断、不摘要、不改写。
- 书单是扩展搜索空间的关系图，不自动等于“有成绩”；应优先使用上榜作品锚定的书单、官方推荐/高关注书单等有额外社会证明的入口。
- Case 池跨日期累积，只增不减。
- 采集阶段不先总结套路、Motion、趋势或市场理论。
- 排名、作者等级、热度、字数、标签等可以作为采集内部元数据，但不进入 Seed 创作输入。

下面的外部项目有些只解决了其中一部分。借它们的“手”，不把它们的目标当成我们的目标。

## 1. tianjiqx/qidian_booklist_spider

GitHub：

- https://github.com/tianjiqx/qidian_booklist_spider

### 它已经做过什么

README 明确说明：

- 从起点书单入口开始爬；
- 保存 `booklist`、书单里的 `book`、以及 `bookdetail`；
- 数据写入 MySQL；
- 对书单数据做统计；
- 后续计划根据“用户收藏书单列表”继续扩大书单集合；
- 考虑 Bloom Filter、并发、多线程、代理等大规模采集工程问题。

### 对我们最有价值的思想

它已经碰到了我们现在准备继续走的一条路：

```text
一个书单
↓
其中的书
↓
用户收藏/关联的更多书单
↓
更多书
↓
继续扩
```

这证明“书单不是静态列表，而是可继续遍历的关系网络”很早就有人实际做过。

### 我们不跟它走的地方

它最终想做：

- 数据库存储；
- 书单统计；
- 推荐榜单 / 推荐书籍。

我们最终要的是：

```text
市场过滤后的大量真实 Case
=
书名
+
完整简介
```

不把推荐算法、书单统计当主目标。

### 以后什么时候回来翻

当我们开始做：

- 书单 → 书单的二跳/多跳扩展；
- URL 去重；
- 大规模断点续跑；
- Bloom Filter；
- 采集速度优化；
- 长期持久化 Case Graph；

优先回来参考这个项目。

## 2. Beat1ngHeart/Novel-Ranking-Scanner

GitHub：

- https://github.com/Beat1ngHeart/Novel-Ranking-Scanner

### 它已经做过什么

这是一个比较完整的“网文扫榜工程”：

```text
榜单
↓
作品详情
↓
缓存
↓
过滤
↓
分析
↓
Markdown 报告
```

README 中明确包含：

- 起点 + 番茄；
- 起点移动端策略；
- 单书详情缓存；
- 断点续跑；
- 跨榜去重；
- 原始 JSON、详情缓存、分析结果、报告分层存储；
- 简介分析；
- 403 退避和反爬处理。

### 对我们最有价值的思想

主要是工程层：

- **榜单与详情分两阶段**；
- 单书详情缓存，避免重复访问；
- 失败后断点续跑；
- 跨榜同书只抓一次详情；
- raw / details / outputs 分层；
- debug HTML 留档，方便页面结构变化后修解析器。

这些都适合我们以后把 Case 数量做大。

### 我们不跟它走的地方

它最后会继续：

- 分类趋势分析；
- 标题模式分析；
- 简介开篇统计；
- 作者等级分析；
- 生成写作建议。

我们的采集层应停在：

```text
书名 + 完整简介
```

分析与 Seed 生成属于下游，不能在采集阶段压缩原始 Case。

### 以后什么时候回来翻

当我们需要：

- 起点分页；
- 详情缓存；
- 增量采集；
- retry / backoff；
- 原始抓取和最终 Case 池分层；

优先参考。

## 3. d3nnywong/qidian-mcp-server

GitHub：

- https://github.com/d3nnywong/qidian-mcp-server

### 它已经做过什么

README 描述的是一个专门给 Agent / Claude Code 使用的起点 MCP：

- 扫描多个起点榜单和品类；
- 获取作品详情：标题、作者、简介、字数、推荐数据；
- 获取章节结构；
- 获取书评；
- 做品类趋势；
- 做 AI 辅助拆书。

### 对我们最有价值的思想

它证明可以把起点采集层做成一个**LLM 原生查询后端**：

```text
LLM
↓
工具调用
↓
起点数据
↓
作品 / 简介 / 章节 / 评论
```

以后如果我们的 Case 池太大，不适合一次把整个 Markdown 喂给模型，可以考虑：

```text
Case Store
↓
语义检索 / 条件检索
↓
只把本轮最相关的真实 Case 送给 Seed 算法
```

MCP 只是可能的接口形态，不是当前必须方案。

### 我们不跟它走的地方

它偏“一本一本查询 / 拆书工具”。

我们当前首先要解决的是：

> **大规模、长期、自动积累 Case。**

先把数据池做起来，再讨论接口。

## 4. lornshrimp/Lorn.NovelWriteSkills

GitHub：

- https://github.com/lornshrimp/Lorn.NovelWriteSkills

重点文档：

- `CommonSkills/通用-分析竞对作品/SKILL.md`
- `CommonSkills/通用-分析竞对作品/references/榜单检索与样本池确定规则.md`

### 它已经做过什么

它在文档层把“榜单 → 样本池”写得很明确：

```text
TopN 候选池
↓
正式深拆样本池
↓
边界 / 旁证样本
```

而且把起点市场数据、榜单、书单、作品页、正文、评论都视作竞品研究证据。

### 对我们最有价值的思想

它和我们共享一个底层前提：

> 不从模型脑内先想“什么书值得研究”，而是先用真实市场作品建立样本池。

也就是：

```text
真实市场证据
↓
样本
↓
后续创作研究
```

这个方向与我们一致。

### 我们不跟它走的地方

它会主动把候选池收缩到 3–5 本做深度竞品分析。

我们当前的目标相反：

> **尽量保留大量原始 Case，让原 Case 自己参与 Seed 碰撞。**

所以它的“候选池思维”值得借，但“收缩成少量主样本 + 总结结论”不能提前套到我们的采集阶段。

## 5. wq1131173682/wqsumeru · wq-scan

GitHub：

- https://github.com/wq1131173682/wqsumeru

文件：

- `skills/wq-scan/SKILL.md`

### 它已经做过什么

它也是 Skill 化的网文市场扫描：

- 抓公开榜单；
- 解析书名、作者、题材、简介、排名；
- 缓存；
- 趋势分析；
- 竞品拆解；
- 最后生成写作指南。

### 对我们最有价值的思想

主要证明：

- “扫榜”可以独立做成 Skill；
- 数据抓取和创作工作流可以直接连接；
- 同一天同榜单缓存是必要工程优化。

### 我们不跟它走的地方

它的主路线仍然是：

```text
榜单
↓
统计
↓
趋势
↓
套路
↓
写作指南
```

而我们是：

```text
榜单
↓
真实 Case
↓
继续保留真实 Case
↓
Seed 时再发生碰撞
```

不要把我们的采集 Skill 重新做成趋势分析器。

- 自动获取番茄、起点、晋江公开排行榜；
- 榜单完成后进入 AI 分析；


- 热门信号；
- 类型趋势；

> **保留原始书名 + 完整简介，让真实作品本身拥有更高语义权。**

## 7. zeyu-acad/Qidian-Webnovel-Corpus

GitHub：

- https://github.com/zeyu-acad/Qidian-Webnovel-Corpus

### 它已经做过什么

这是研究型语料库。

它通过人工搜索 Webnovel 已完结翻译作品，再映射回对应起点原作，最后形成 110 本作品的数据集，并收集：

- 作品映射；
- 免费章节元数据；
- 章节 ID；
- 读者评论；
- 回复；
- 用户层级等研究数据。

### 对我们最有价值的思想

它说明长期 Case 库最好拥有稳定的“作品身份”。

即使最终给 Seed 的输入只有：

```text
书名
+
简介
```

内部最好仍能保留：

- platform；
- book_id；
- source_url；

否则以后同名书、改名书、简介更新、多来源映射都会难以管理。

### 另一个提醒

长期积累第三方内容时，要区分：

- 我们内部研究/检索需要的元数据；
- 最终能公开分发的内容；
- 可能受到平台条款、版权或数据授权约束的数据。

当前 Case 池以作品公开简介为核心，不要无必要扩成正文镜像库。

# 10. 当前不做的事情

为了避免参考项目把方向带偏，以下事项暂不进入当前采集主线：

- 不做题材热度报告；
- 不统计标题关键词；
- 不分析作者等级；
- 不按榜单名给作品不同权重；
- 不优先新书；
- 不把书单当作无条件质量证明；
- 不自动生成“市场建议”；
- 不在采集阶段提炼 Motion；
- 不抓整本正文；
- 不为追求字段完整度牺牲 Case 数量和简介保真。

当前优先级始终是：

```text
起点
↓
更多有市场证明的作品
↓
更多真实书单关系
↓
更多完整简介
↓
更大的累计 Case 池
```

# 11. 未来可能演化出的结构

当 Case 池足够大以后，再考虑：

```text
Qidian Case Graph
├── Book
│   ├── book_id
│   ├── title
│   ├── full_intro
│   └── source_url
│
├── Evidence
│   ├── appeared_on_rank
│   ├── appeared_in_followed_booklist
│   └── first_seen / last_seen
│
└── Relation
    ├── book -> booklist
    ├── booklist -> book
    └── book -> related book
```

但这只是内部数据结构。

给故事 Seed 的接口仍然可以保持最简单的：

```text
《书名》
完整简介
```

复杂度留在采集器内部，不污染创作输入。
